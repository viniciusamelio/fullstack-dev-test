# smash-api

AI-powered gift-card message suggester backend. A single endpoint takes an
`occasion` + `relationship` and returns 3 short gift-card message
suggestions generated by an LLM, with a two-stage fallback when the LLM is
unavailable. See [`REQUIREMENTS.md`](./REQUIREMENTS.md) for the
original brief and [`QUALITY.md`](./QUALITY.md) /
[`quality-gates.json`](./quality-gates.json) for the testing bar every
change must clear.

## Stack

- **Runtime:** Node.js **v22+** (executed via `tsx` in dev, plain `node` on
  the `tsc` build output in prod). Originally targeted v20; raised after
  discovering `better-sqlite3@13`'s native binding (`NAPI_VERSION=10`)
  reliably segfaults on `new Database(...)` under Node 20 — reproduced
  identically with both its bundled prebuilt binary and a fresh
  from-source build, so it's a real Node-version constraint, not an
  environment quirk. See `Dockerfile`'s top comment for how this was
  diagnosed.
- **Package manager / script runner:** Bun (`bun install`, `bun run <script>`)
  — Bun is not the runtime here, only tooling.
- **API layer:** [oRPC](https://orpc.dev) — contract-first (`@orpc/contract`),
  implemented and exposed as a plain REST route via `@orpc/openapi`'s
  `OpenAPIHandler` over `node:http` (no Hono/Express). Chosen over oRPC's
  native RPC handler so any client can just do a normal JSON POST without
  needing an oRPC-specific client — a typed HTTP client can still be
  generated from the contract's OpenAPI document (`GET /spec.json`, see
  below) for TS/JS consumers, e.g. via Hey API's `openapi-ts`.
- **Validation:** zod (v4), shared between the oRPC contract and the LLM's
  structured-output schema.
- **LLM:** [ai-sdk](https://ai-sdk.dev) (`ai` + `@ai-sdk/openai`),
  `generateText` with `output: Output.object({ schema })` for guaranteed
  `{ messages: [string, string, string] }` structured output.
- **DB:** SQLite via `better-sqlite3`, [Drizzle ORM](https://orm.drizzle.team)
  (`drizzle-orm/better-sqlite3`), migrations via `drizzle-kit`.
- **Error handling:** [`better-result`](https://better-result.dev) 3.0
  (`Result`/`TaggedError`) everywhere instead of raw `try`/`catch` — see
  below.
- **Tests:** vitest + `@vitest/coverage-v8`.
- **Lint/format:** [Biome](https://biomejs.dev) (`biome.json`) — replaces ESLint + Prettier, also sorts imports.

## Architecture: ports and adapters

`api/src/` is split into four layers with a strict one-way dependency rule:
**domain ← data ← infra**; **presentation** depends on `domain` (types) and
`data` (usecase interface) and wires everything together via a composition
root, but nothing ever depends back on `presentation` or `infra` from
`domain`/`data`.

```
api/src/
  domain/          # enums, models, usecase *interfaces*. No I/O, no framework.
    enums/occasion.ts, enums/relationship.ts
    models/suggestion-request.ts, models/suggestion-result.ts
    usecases/generate-suggestions.ts        # interface only

  data/            # usecase *implementation* + the ports (protocols) it needs.
    protocols/     # interfaces infra must implement: LlmSuggestionGateway,
                    # PromptRunRepository, SuggestionResultRepository,
                    # FallbackMessageProvider, Logger
    errors/        # TaggedError classes for each protocol's failure mode
    usecases/db-generate-suggestions.ts     # the fallback-chain orchestration

  infra/           # concrete adapters implementing data's protocols.
    llm/           # OpenAI adapter (ai-sdk) + versioned prompt templates
    db/            # Drizzle schema, client, migrations, repositories
    fallback/      # static-fallback-message-provider.ts
    logging/       # console-logger.ts
    config/        # env.ts (zod-validated env)

  presentation/    # oRPC contract/router, HTTP server, composition root.
    contracts/suggestions.contract.ts       # oc contract: zod schemas + .route()
    routers/suggestions.router.ts           # os.contract(...).handler(...)
    http/server.ts, http/main.ts, http/error-mapper.ts
    factories/make-generate-suggestions.ts  # composition root
```

Why this split: `data/usecases/db-generate-suggestions.ts` (the fallback
chain — the one piece of actual business logic in this service) is
testable with pure in-memory mocks of its ports, with zero knowledge of
OpenAI, SQLite, or oRPC. Swapping the LLM provider, the DB, or the HTTP
framework only touches `infra`/`presentation`.

## The endpoint

Single route: `POST /suggestions`

```json
// request
{ "occasion": "birthday", "relationship": "friend" }

// response (200 — always, even when the LLM failed)
{ "messages": ["...", "...", "..."], "source": "llm" }
```

- `occasion` / `relationship`: see `domain/enums/occasion.ts` and
  `domain/enums/relationship.ts` for the full list. Invalid values → `400`
  (zod validation, via the oRPC contract).
- `source`: `"llm" | "cache" | "static"` — tells the caller which stage of
  the fallback chain produced the messages. Never exposed as an error to
  the client; see below.
- Rate limited (10/min per IP, see "Rate limiting" below) → `429` with a
  `Retry-After` header, before the request reaches this handler at all.

**`GET /spec.json`** — the OpenAPI 3.1 document for the contract above
(`presentation/http/openapi-spec.ts`, `@orpc/openapi`'s `OpenAPIGenerator`
+ `@orpc/zod/zod4`'s schema converter — note the `/zod4` subpath, the bare
`@orpc/zod` converter silently produces empty schemas against zod v4).
Generated once per server instance and cached (the contract is static).
This is what the frontend points a client generator at — e.g. Hey API's
`openapi-ts` (`orpc` plugin) to get a typed oRPC-compatible client, or any
other OpenAPI-driven codegen, from `http://localhost:3000/spec.json`.

## The fallback chain

`data/usecases/db-generate-suggestions.ts`:

1. Call the LLM (`LlmSuggestionGateway.generate`). On success: persist an
   audit row (`prompt_runs`, `status: "success"`) and the result
   (`suggestion_results`, `source: "llm"`), return the 3 messages.
2. On LLM failure (timeout/429/5xx/malformed output — anything): persist
   the audit row (`status: "llm_failed"`, error captured), then look up
   the latest **previously successful LLM result** for the same
   `occasion` + `relationship` + `promptVersion`
   (`SuggestionResultRepository.findLatestBySignature`, which only ever
   considers `source: "llm"` rows — a stale cache/static result can never
   cascade into becoming "the cache").
   - Found → persist `source: "cache"`, return it.
   - Not found (or the lookup itself fails) → fall to
     `FallbackMessageProvider` (static, hardcoded, per-occasion,
     infallible), persist `source: "static"`, return it.

Every call is audited (`prompt_runs`) and every returned result is
persisted (`suggestion_results`) regardless of source — this is what makes
step 2's lookup possible and gives a cost-control audit trail (see
"Cost control" below). Persistence failures along the way are logged and
never block the response — a DB hiccup while writing the audit row must
not turn a successful LLM answer into a 500.

## Prompt versioning

Templates live in code under `infra/llm/prompts/` (`v1-suggestion-prompt.ts`
today), each exporting a `PROMPT_VERSION` string bumped whenever the
template changes in a way that affects output. `promptVersion` is
persisted on every `prompt_runs`/`suggestion_results` row, so:

- cost/quality can be tracked per template version;
- the cache-fallback lookup in step 2 above is scoped to the *current*
  version, so a stale cached answer from an old prompt template can never
  be served once the template has moved on.

To add a new template version: add `infra/llm/prompts/v2-*.ts`, bump
`PROMPT_VERSION`, wire it in `presentation/factories/make-generate-suggestions.ts`.

## Rate limiting

`presentation/http/rate-limiter.ts`: a fixed-window in-memory limiter
(`RATE_LIMIT_MAX` requests per `RATE_LIMIT_WINDOW_MS`, default `10`/`60000`
— 10/min per IP), checked in `presentation/http/server.ts` before the
request reaches the oRPC handler, keyed by `getClientIp()`
(`presentation/http/client-ip.ts`: `x-forwarded-for` first hop, else the
socket address). Over the limit → `429`, `Retry-After` header (seconds),
`{"error":"rate_limited","retryAfterSeconds":n}` — the LLM/DB are never
touched for a blocked request. Single-process, in-memory: correct for one
instance, would need a shared store (Redis) behind a load balancer, and a
fixed window can allow up to 2x the limit across a window boundary — an
accepted trade-off for a soft per-IP guard, not a strict quota.

## Cost control

Every LLM call attempt is a row in `prompt_runs` (occasion, relationship,
prompt version, model, status, latency, **cost_usd**). This is the audit
trail for tracking spend — query it to see call volume *and actual $
cost* per prompt version, and the cache-fallback layer means a repeated
`occasion`+`relationship` pair during an LLM outage costs zero extra LLM
calls.

`cost_usd` is computed per successful call from `generateText`'s
`usage.inputTokens`/`usage.outputTokens` against a hardcoded
$/1M-token table in `infra/llm/pricing.ts` (`costUsdFor`), keyed by bare
model id — `null` when the model isn't in that table or usage wasn't
reported (e.g. every failed call: there's no completed call to price).
That pricing table is a point-in-time snapshot (checked against OpenAI's
pricing page on the date noted in the file), **not** fetched live — bump
it whenever `OPENAI_MODEL` changes to a model not already listed, and
re-verify the numbers periodically since OpenAI's pricing changes over
time independently of this repo. The model itself (`OPENAI_MODEL`,
default `openai/gpt-5-nano`) is picked for being OpenAI's cheapest model
suitable for this kind of short, low-stakes structured text.

## Error handling: no raw `try`/`catch`

Every fallible operation (LLM call, DB read/write, env parsing) returns
`Result<T, E>` from [`better-result`](https://better-result.dev) instead
of throwing:

- `Result.tryPromise({ try, catch })` wraps an async call that might
  throw/reject, converting the failure into a typed `TaggedError`
  (e.g. `LlmGenerationFailed`, `PersistenceFailed`, `SuggestionLookupFailed`
  in `data/errors/`).
- `Result.isOk` / `Result.match` branch on the outcome without unwinding
  the stack — used throughout `db-generate-suggestions.ts` to implement
  "try this, log and fall through to the next thing on failure" (an
  `orElse`-style chain), which is why that usecase does **not** use
  `Result.gen`'s short-circuit-on-first-`Err` composition — the fallback
  chain deliberately keeps going after an `Err`, `Result.gen` deliberately
  stops.
- `GenerateSuggestions.execute()` is typed `Result<SuggestionResult, never>`
  — by construction, the fallback chain always resolves to `Ok`, so
  `Result.unwrap()` at the router boundary can never throw in practice.

**The one sanctioned exception:** a genuine defect (a thrown exception —
`better-result` calls this a `Panic`, not an `Err`) inside a handler is
never explicitly caught in application code. It propagates out of the
oRPC procedure handler; oRPC itself catches it and returns a sanitized,
generic error response (never the raw error to the client), and
`presentation/http/error-mapper.ts`'s `onError` interceptor logs it
server-side. This is deliberate: masking a real bug as a fake 200 would
be worse than a logged, sanitized 500 — the "never expose a raw LLM/DB
error" guarantee is about the business-error path (which the Result-based
fallback chain already fully covers, see above), not about hiding actual
bugs.

## Commands

Run from `api/`:

```bash
bun install             # install deps
bun run dev              # tsx watch — dev server (needs .env, see below)
bun run build             # tsc -p tsconfig.build.json → dist/
bun run start              # node dist/presentation/http/main.js
bun run typecheck           # tsc --noEmit
bun run lint                  # biome check .
bun run lint:fix               # biome check --write . (auto-fix + organize imports)
bun run test                     # vitest run
bun run test:coverage         # vitest run --coverage (must hit 100%, see QUALITY.md)
bun run db:generate            # drizzle-kit generate (new migration from schema.ts)
bun run db:migrate               # apply migrations to $DB_PATH
```

Or via Docker (`Dockerfile` + `docker-compose.yml`, pnpm-based build —
see that file's top comment for why pnpm/Node 22 specifically):

```bash
cp .env.example .env        # fill in OPENAI_API_KEY
docker compose up --build    # migrations run automatically on container start
```

## Environment

Copy `api/.env.example` to `api/.env`:

| Var | Default | Notes |
|---|---|---|
| `OPENAI_API_KEY` | — | required |
| `OPENAI_MODEL` | `openai/gpt-5-nano` | bare (`gpt-5-nano`) or namespaced (`openai/gpt-5-nano`) — the prefix is stripped before calling OpenAI directly |
| `DB_PATH` | `./data/smash.db` | SQLite file path |
| `PORT` | `3000` | HTTP port |
| `RATE_LIMIT_MAX` | `10` | max requests per IP per window |
| `RATE_LIMIT_WINDOW_MS` | `60000` | rate-limit window size, ms |

## Adding a new occasion or relationship

Add the literal to `domain/enums/occasion.ts` / `relationship.ts`
(`OCCASIONS`/`RELATIONSHIPS` const array — the zod schema in the oRPC
contract and the TS union type both derive from it). If it's an occasion,
also add an entry to `MESSAGES_BY_OCCASION` in
`infra/fallback/static-fallback-message-provider.ts` — that map is a
`Record<Occasion, ...>`, so TS will refuse to compile until every
occasion has a static fallback message set.
